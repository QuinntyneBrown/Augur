# ADR-0004: One Embedded Lockfile per Angular Dependency Set

**Date:** 2026-10-07
**Category:** backend
**Status:** Accepted
**Deciders:** Quinntyne Brown (project owner)

## Context

Every emitted Angular workspace must ship a `package-lock.json` that matches its `package.json` (L2-052), so `npm ci` installs exactly the tested dependency tree. Augur must never run `npm` while emitting (L2-058). The Angular design assumed one static lockfile, but the dependency set changes with four decisions: `ui-library` adds `@angular/material` and `@angular/cdk`, `state-management` adds `@ngrx/signals`, `server-side-rendering` adds `@angular/ssr`, `@angular/platform-server`, and Express, and `authentication` adds `angular-oauth2-oidc`. `npm ci` rejects a lockfile whose root dependencies differ from `package.json`, so one lockfile cannot serve all 16 combinations.

## Decision

Augur embeds 16 gzip-compressed lockfiles in `Augur.Emission.Angular`, one per dependency set, named `{material|plain}-{store|signals}-{ssr|csr}-{auth|anon}.json.gz`. The project name inside each lockfile is a placeholder that the emitter fills in. `eng/Regenerate-AngularLockfiles.ps1` regenerates all 16: it builds Augur with `AugurBootstrapLockfiles=true`, emits each workspace, and runs `npm install --package-lock-only`. A normal build without a matching lockfile fails emission rather than writing a workspace without one.

## Options Considered

### Option 1: One lockfile per dependency set, generated by a script (chosen)
- **Pros:** Exact, reproducible installs for every plan; emission stays offline; about 1 MB of compressed resources.
- **Cons:** Regeneration is a release task whenever a version changes.

### Option 2: One lockfile for a superset `package.json`
- **Pros:** One file.
- **Cons:** Every workspace would carry Material, NgRx, SSR, and OIDC dependencies, contradicting `ui-library=none` (L2-052 AC1).

### Option 3: No lockfile
- **Pros:** Simplest.
- **Cons:** Breaks L2-052 and makes emitted builds non-reproducible.

## Consequences

- The slow suite's `npm ci` is the test that each lockfile matches its `package.json`; fast tests check that a lockfile is emitted and named after the project.
- `CONTRIBUTING.md` documents when to run the script.
