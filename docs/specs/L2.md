# L2 - Detailed Requirements

## Conventions used in this document

- **Exit codes** (referenced throughout):

  | Code | Meaning |
  |------|---------|
  | 0 | Success |
  | 1 | Unexpected internal error |
  | 2 | Invalid usage or invalid input (arguments, specification, plan, lockfile, script) |
  | 3 | One or more decisions could not be resolved |
  | 4 | Decisions API failure |
  | 5 | Output conflict or file-system write failure |
  | 130 | Cancelled by the user |

- **Input hash:** SHA-256 over the specification text (normalized to LF line endings, UTF-8) followed by the bytes of each image in the order given on the command line.
- **Question hash:** SHA-256 over the canonical JSON of a decision's catalog definition (type, instructions, options or levels and their descriptions, thresholds).
- **Reference machine:** 4 CPU cores, 16 GB RAM, SSD storage, .NET 10 runtime already installed.

---

## L2-001: Commands
**Traces to:** L1-001

The CLI command is `augur`. It shall provide the following subcommands:

| Command | Purpose |
|---------|---------|
| `augur plan` | Resolve decisions for a specification and write a `GenerationPlan` |
| `augur emit` | Emit code from an existing `GenerationPlan` |
| `augur generate` | Run `plan` then `emit` in one step |
| `augur explain` | Show how each decision in a lockfile was reached |
| `augur catalog` | List the decisions in the built-in catalog and their allowed answers |
| `augur schema plan` | Print the JSON Schema for `GenerationPlan` |

**Acceptance Criteria:**
1. Given Augur is installed, when the user runs `augur --help`, then the output lists all six commands with a one-line description each and the exit code is 0.
2. Given any command, when the user runs `augur <command> --help`, then the output lists every option for that command with its description and default value, and the exit code is 0.
3. Given Augur is installed, when the user runs `augur` with no arguments, then the general help is written to stderr and the exit code is 2.
4. Given Augur is installed, when the user runs `augur frobnicate`, then stderr contains "Unknown command 'frobnicate'" and the exit code is 2.
5. Given a valid command, when the user passes an unknown option `--nope`, then stderr names the unknown option and the exit code is 2.

## L2-002: Version information
**Traces to:** L1-001

`augur --version` shall print the tool version and the catalog version.

**Acceptance Criteria:**
1. Given Augur version 1.2.3 with catalog version 4, when the user runs `augur --version`, then stdout is exactly `augur 1.2.3 (catalog 4)` followed by a newline and the exit code is 0.

## L2-003: Exit codes and output streams
**Traces to:** L1-001

Every command shall exit with one of the codes in the Conventions table. Machine-readable output (plan JSON, schema JSON, `--json` output) shall be written only to stdout. Progress, warnings, errors, and logs shall be written only to stderr.

**Acceptance Criteria:**
1. Given a valid specification and a complete scripted answer file, when the user runs `augur plan --spec spec.md --oracle-script answers.json` with no `--out`, then stdout contains only the plan JSON (parseable as JSON with nothing else on stdout) and the exit code is 0.
2. Given any failure scenario defined in this document, when the command ends, then the exit code matches the code that scenario specifies and stderr contains a single-line error message beginning with `error:`.
3. Given an unhandled internal exception, when the command ends, then the exit code is 1, stderr contains `error:` with the exception message, and the stack trace appears only when `--verbosity diagnostic` is set.

---

## L2-004: Cancellation
**Traces to:** L1-001

When the user presses Ctrl+C (SIGINT) or the process receives SIGTERM, Augur shall cancel in-flight API requests, stop work, leave existing files unchanged, and exit with code 130.

**Acceptance Criteria:**
1. Given `augur generate` is waiting on a Decisions API request, when SIGINT is received, then the HTTP request is cancelled, the process exits with code 130 within 2 seconds, and the lockfile and output directory are byte-identical to their state before the run.
2. Given `augur emit` is writing files, when SIGINT is received, then the output directory contains either none of the run's files or its prior contents unchanged (see L2-034), and the exit code is 130.

---

## L2-005: Specification text input
**Traces to:** L1-002

`augur plan` and `augur generate` shall require `--spec <path>`. The value `-` reads the specification from stdin. The specification shall be UTF-8 text (BOM permitted) of at least 1 non-whitespace character and at most 256 KiB.

**Acceptance Criteria:**
1. Given no `--spec` option, when the user runs `augur plan`, then stderr says `--spec` is required and the exit code is 2.
2. Given `--spec missing.md` where the file does not exist, when the user runs `augur plan`, then stderr names the missing path and the exit code is 2.
3. Given a specification file that is empty or contains only whitespace, when the user runs `augur plan`, then stderr says the specification is empty and the exit code is 2.
4. Given a specification file of 262,145 bytes, when the user runs `augur plan`, then stderr says the specification exceeds 256 KiB and the exit code is 2, and no API request is made.
5. Given a specification file of exactly 262,144 bytes of valid UTF-8, when the user runs `augur plan` with a complete scripted answer file, then the exit code is 0.
6. Given a specification file containing invalid UTF-8 byte sequences, when the user runs `augur plan`, then stderr says the file is not valid UTF-8 and the exit code is 2.
7. Given `--spec -` and the specification piped on stdin, when the user runs `augur plan`, then the plan is produced exactly as if the same text had been read from a file.

---

## L2-006: Image input
**Traces to:** L1-002

`augur plan` and `augur generate` shall accept `--image <path>` up to 4 times. Each image shall be PNG, JPEG, or WEBP, identified by its file signature (not its extension), and at most 10 MiB. Images shall be sent to the Decisions API as base64 `data:` URLs inside the same user message as the specification text.

**Acceptance Criteria:**
1. Given a PNG file named `sketch.jpg`, when it is passed with `--image`, then it is accepted and sent with media type `image/png`.
2. Given a text file named `sketch.png`, when it is passed with `--image`, then stderr says the file is not a supported image and the exit code is 2.
3. Given 5 `--image` options, when the user runs `augur plan`, then stderr says at most 4 images are allowed and the exit code is 2.
4. Given an image of 10,485,761 bytes, when it is passed with `--image`, then stderr says the image exceeds 10 MiB and the exit code is 2.
5. Given a specification and two images, when a Decisions API request is sent, then the request `input` contains one user message whose content is an `input_text` part with the specification followed by two `input_image` parts with `data:` URLs, in command-line order.
6. Given two runs with the same specification and the same images in a different order, when the input hash is computed, then the two hashes differ.

## L2-007: Built-in decision catalog
**Traces to:** L1-003

The catalog shall define each decision with: a unique `id`, a `type` (`predicate`, `choice`, or `score`), `instructions`, the closed answer set (options or levels, each with a description), confidence thresholds, a `default` answer, and an optional `when` dependency on other decisions. Catalog version 2 shall contain these decisions:

| id | type | answers | default | when |
|----|------|---------|---------|------|
| `target` | choice | `fullstack`, `dotnet`, `angular`, `other` | `fullstack` | always |
| `authentication` | predicate | `true`, `false` | `false` | always |
| `architecture` | choice | `clean-architecture`, `vertical-slice`, `minimal-api`, `other` | `clean-architecture` | `target` is `fullstack` or `dotnet` |
| `persistence` | choice | `ef-core-sqlserver`, `ef-core-postgresql`, `ef-core-sqlite`, `none`, `other` | `ef-core-sqlite` | `target` is `fullstack` or `dotnet` |
| `background-processing` | predicate | `true`, `false` | `false` | `target` is `fullstack` or `dotnet` |
| `domain-complexity` | score | levels 0 `trivial`, 1 `crud`, 2 `business-rules`, 3 `complex-domain`; resolves to `cqrs` = `true` when score >= 2.0, else `false` | `false` | `architecture` is `clean-architecture` or `vertical-slice` |
| `ui-library` | choice | `angular-material`, `none`, `other` | `angular-material` | `target` is `fullstack` or `angular` |
| `state-management` | choice | `signals`, `ngrx-signal-store`, `other` | `signals` | `target` is `fullstack` or `angular` |
| `server-side-rendering` | predicate | `true`, `false` | `false` | `target` is `fullstack` or `angular` |

**Acceptance Criteria:**
1. Given catalog version 2, when the catalog is loaded, then it contains exactly the nine decisions above with the listed answer sets, defaults, and dependencies.
2. Given any `choice` decision in the catalog, when its options are inspected, then one option is `other`.
3. Given any decision in the catalog, when its definition is inspected, then every option or level has a non-empty description and the `default` is a member of its answer set.
4. Given a catalog in which a `when` clause references an undefined decision or forms a cycle, when Augur starts, then it exits with code 1 and names the invalid decision. (This guards against shipping a broken catalog; it is verified by a build-time test of the catalog loader with a malformed catalog fixture.)

## L2-008: Catalog listing
**Traces to:** L1-003

`augur catalog` shall list every decision with its id, type, allowed answers, default, and dependency. `--json` shall output the same information as JSON.

**Acceptance Criteria:**
1. Given catalog version 2, when the user runs `augur catalog`, then stdout lists all nine decisions, each with its id, type, allowed answers, and default, and the exit code is 0.
2. Given catalog version 2, when the user runs `augur catalog --json`, then stdout is a JSON object with `catalogVersion: 2` and a `decisions` array of nine entries whose `id`, `type`, `answers`, `default`, and `when` match the table in L2-007.

---

## L2-009: Catalog versioning
**Traces to:** L1-003

The catalog shall carry an integer version. Any change to a decision's instructions, answers, descriptions, or thresholds shall change that decision's question hash and shall require the catalog version to be incremented.

**Acceptance Criteria:**
1. Given two catalog definitions that differ only in one option's description, when the question hashes are computed, then only the hash of the changed decision differs.
2. Given a plan file, when it is produced, then it records the `catalogVersion` used.

---

## L2-010: Tree traversal order and dependencies
**Traces to:** L1-004

Decisions shall be evaluated in dependency levels: a decision is evaluated only after every decision named in its `when` clause has been resolved. A decision whose `when` clause evaluates to false shall be marked `skipped`, shall not be sent to the Decisions API, and shall take no value in the plan. A `when` clause that refers to a skipped decision evaluates to false.

**Acceptance Criteria:**
1. Given scripted answers where `target` resolves to `dotnet` and `architecture` resolves to `minimal-api`, when `augur plan` runs, then `domain-complexity` is recorded as `skipped`, is not requested from the oracle, and the plan has no `cqrs` value.
2. Given scripted answers where `target` resolves to `dotnet` and `architecture` resolves to `clean-architecture`, when `augur plan` runs, then `domain-complexity` is evaluated after `architecture` and the plan contains a `cqrs` value.
3. Given the Decisions API oracle, no lockfile, and no overrides, when `augur plan` runs, then the first request contains exactly `target` and `authentication`; the second request contains every decision whose `when` clause depends only on `target` and evaluates to true; and `domain-complexity`, when applicable, is sent in a third request.
4. Given scripted answers where `target` resolves to `angular`, when `augur plan` runs, then `architecture`, `persistence`, `background-processing`, and `domain-complexity` are `skipped`, and the plan contains values only for `target`, `authentication`, `ui-library`, `state-management`, and `server-side-rendering`.
5. Given scripted answers where `target` resolves to `dotnet`, when `augur plan` runs, then `ui-library`, `state-management`, and `server-side-rendering` are `skipped`.

---

## L2-011: Predicate decisions
**Traces to:** L1-004

A predicate decision has an upper threshold (default 0.80) and a lower threshold (default 0.20). It resolves to `true` when probability >= upper, to `false` when probability <= lower, and is low-confidence otherwise.

**Acceptance Criteria:**
1. Given `authentication` returns probability 0.80, when the decision is resolved, then the value is `true`.
2. Given `authentication` returns probability 0.20, when the decision is resolved, then the value is `false`.
3. Given `authentication` returns probability 0.50, when the decision is resolved, then the decision is low-confidence and the fallback policy (L2-019) is applied.

---

## L2-012: Choice decisions
**Traces to:** L1-004

A choice decision has a minimum confidence (default 0.70). It resolves to the returned `choice` when `confidence` >= the minimum and the choice is not `other`; otherwise it is low-confidence.

**Acceptance Criteria:**
1. Given `architecture` returns choice `vertical-slice` with confidence 0.70, when the decision is resolved, then the value is `vertical-slice`.
2. Given `architecture` returns choice `vertical-slice` with confidence 0.69, when the decision is resolved, then the decision is low-confidence.
3. Given `architecture` returns choice `other` with confidence 0.95, when the decision is resolved, then the decision is low-confidence.

---

## L2-013: Score decisions
**Traces to:** L1-004

A score decision has a minimum confidence (default 0.70) and a cut-off that maps the continuous score to its resolved value. For `domain-complexity`, `cqrs` is `true` when score >= 2.0.

**Acceptance Criteria:**
1. Given `domain-complexity` returns score 2.0 with confidence 0.80, when the decision is resolved, then `cqrs` is `true`.
2. Given `domain-complexity` returns score 1.99 with confidence 0.80, when the decision is resolved, then `cqrs` is `false`.
3. Given `domain-complexity` returns score 2.5 with confidence 0.50, when the decision is resolved, then the decision is low-confidence.

---

## L2-014: Overrides
**Traces to:** L1-004

`--set <id>=<value>` (repeatable) shall resolve a decision deterministically without calling any oracle. Overridden decisions are recorded with source `override`. Overrides also determine `when` clauses of dependent decisions.

**Acceptance Criteria:**
1. Given `--set target=dotnet --set architecture=minimal-api`, when `augur plan` runs against the Decisions API, then no request contains an `architecture` question, the plan value is `minimal-api` with source `override`, and `domain-complexity` is `skipped`.
2. Given `--set colour=blue`, when `augur plan` runs, then stderr says `colour` is not a catalog decision, lists the valid ids, and the exit code is 2.
3. Given `--set architecture=hexagonal`, when `augur plan` runs, then stderr lists the allowed values for `architecture` and the exit code is 2.
4. Given `--set architecture=other`, when `augur plan` runs, then stderr says `other` cannot be set explicitly and the exit code is 2.
5. Given `--set authentication=true`, when `augur plan` runs, then the override is accepted for a predicate decision.
6. Given every applicable decision is overridden, when `augur plan` runs without `OPENAI_API_KEY` set, then the plan is produced, no network request is made, and the exit code is 0.
7. Given `--set target=angular --set architecture=minimal-api`, when `augur plan` runs, then stderr says `architecture` does not apply when `target` is `angular` and the exit code is 2.

---

## L2-015: Closed answer enforcement
**Traces to:** L1-004

An answer from any source (API, lockfile, script, user) that is not a member of the decision's answer set, or a probability, confidence, or score outside its valid range, shall be rejected and never used.

**Acceptance Criteria:**
1. Given the Decisions API returns choice `serverless` for `architecture`, when the response is processed, then stderr reports an invalid response naming the decision and value, and the exit code is 4.
2. Given the Decisions API returns probability 1.3 for `authentication`, when the response is processed, then the exit code is 4.
3. Given a score decision with 4 levels and the API returns score 3.2, when the response is processed, then the exit code is 4.
4. Given a scripted answer file with choice `serverless` for `architecture`, when `augur plan` runs, then stderr names the invalid entry and the exit code is 2.

---

## L2-016: Decisions API requests
**Traces to:** L1-005

Augur shall send `POST {baseUrl}/v1/decisions` with a JSON body containing `model`, `input`, and `questions`. Each question's `name` shall equal the catalog decision id. The default base URL is `https://api.openai.com`; it can be changed with the `AUGUR_OPENAI_BASE_URL` environment variable. The default model is `gpt-6-luna`; it can be changed with `--model`.

**Acceptance Criteria:**
1. Given a stub HTTP server, when `augur plan` runs, then each request is a `POST` to `/v1/decisions` with `Content-Type: application/json`, `Authorization: Bearer <key>`, a body with `model: "gpt-6-luna"`, and one question per pending decision whose `name` is the decision id.
2. Given `--model gpt-6-luna-2026-09`, when a request is sent, then the body's `model` is `gpt-6-luna-2026-09`.
3. Given a `choice` decision, when it is sent, then each option appears with its `value` and `description` from the catalog; given a `score` decision, each level appears in order with its `label` and `description`.

---

## L2-017: Transient failure handling
**Traces to:** L1-005

Augur shall retry a request that fails with HTTP 408, 429, 500, 502, 503, 504, or a network error, up to 3 retries, using exponential backoff with jitter starting at 1 second and capped at 20 seconds. When a `Retry-After` header is present, Augur shall wait at least that long. HTTP 400, 401, 403, 404, and 422 shall not be retried.

**Acceptance Criteria:**
1. Given a stub server that returns 503 twice and then a valid response, when `augur plan` runs, then 3 requests are made and the exit code is 0.
2. Given a stub server that always returns 503, when `augur plan` runs, then exactly 4 requests are made, stderr reports the final status code and the response's request id, and the exit code is 4.
3. Given a stub server that returns 429 with `Retry-After: 2`, when Augur retries, then the next request is sent no sooner than 2 seconds later.
4. Given a stub server that returns 401, when `augur plan` runs, then exactly 1 request is made, stderr says the API key was rejected, and the exit code is 4.

---

## L2-018: Request timeout
**Traces to:** L1-005

Each HTTP attempt shall time out after 30 seconds by default, configurable with `--timeout <seconds>` (1 to 300). A timed-out attempt counts as a transient failure under L2-017.

**Acceptance Criteria:**
1. Given `--timeout 2` and a stub server that never responds, when `augur plan` runs, then each attempt is abandoned after 2 seconds (±0.5 s), 4 attempts are made, and the exit code is 4.
2. Given `--timeout 0` or `--timeout 301`, when the command is parsed, then stderr states the allowed range and the exit code is 2.

---

## L2-019: Low-confidence policy
**Traces to:** L1-006

`--on-low-confidence <default|prompt|fail>` shall select how low-confidence decisions are resolved. When the option is omitted, the policy is `prompt` if stdin and stderr are both terminals, and `fail` otherwise.

**Acceptance Criteria:**
1. Given `--on-low-confidence default` and `architecture` is low-confidence, when `augur plan` runs, then `architecture` resolves to `clean-architecture` with source `fallback`, stderr warns that the default was used, and the exit code is 0.
2. Given `--on-low-confidence fail` and `architecture` is low-confidence, when `augur plan` runs, then stderr lists every low-confidence decision in that dependency level with its returned answer and confidence, no plan is written, and the exit code is 3.
3. Given the option is omitted and stdin is redirected, when a decision is low-confidence, then the `fail` behaviour applies.

---

## L2-020: Interactive prompt
**Traces to:** L1-006

Under the `prompt` policy, Augur shall write to stderr the decision id, its instructions, and its answers other than `other` numbered from 1 in descending order of returned probability (each with its probability formatted to two decimals), then read one line from stdin. The user can enter either the number or the value. An empty line selects the catalog default. After 3 invalid entries the command exits with code 3.

**Acceptance Criteria:**
1. Given the `prompt` policy and low-confidence `persistence`, when the user enters `2`, then the second listed answer is used and recorded with source `user`.
2. Given the same prompt, when the user enters `ef-core-postgresql`, then that value is used with source `user`.
3. Given the same prompt, when the user enters an empty line, then the default `ef-core-sqlite` is used with source `user`.
4. Given the same prompt, when the user enters `9`, `foo`, and `other` in turn, then each entry is re-prompted with an error, and after the third the exit code is 3.

---

## L2-021: Confidence threshold override
**Traces to:** L1-006

`--min-confidence <0..1>` shall replace the minimum confidence of every choice and score decision for the run. It shall not change predicate thresholds.

**Acceptance Criteria:**
1. Given `--min-confidence 0.9` and `architecture` returns confidence 0.85, when the decision is resolved, then it is low-confidence.
2. Given `--min-confidence 1.5`, when the command is parsed, then the exit code is 2.

---

## L2-022: Lockfile contents
**Traces to:** L1-007

After `augur plan` or `augur generate` resolves its decisions, it shall write a lockfile (default `./decisions.json`, configurable with `--lock <path>`) containing: `lockfileVersion`, `catalogVersion`, `inputHash`, and an `entries` array. Each entry holds `id`, `questionHash`, `source` (`api`, `fallback`, `user`, or `script`), `value`, the raw result (`probability`, or `choice`/`probabilities`/`confidence`, or `score`/`probabilities`/`confidence`), `model` (for source `api`), and `resolvedAt` (UTC ISO-8601). Overridden and skipped decisions shall not be written. The lockfile shall never contain the specification text, image data, or credentials.

**Acceptance Criteria:**
1. Given a run in which `target` resolved to `fullstack`, `architecture` resolved to `clean-architecture`, and all decisions were resolved by the API, when the lockfile is read, then it has 9 entries with source `api`, each with the fields above.
2. Given a run with `--set target=dotnet --set architecture=minimal-api`, when the lockfile is read, then it has no `target`, `architecture`, or `domain-complexity` entry.
3. Given any lockfile written by Augur, when searched for any 32-character substring of the specification or for the API key, then neither is found.

---

## L2-023: Lockfile replay
**Traces to:** L1-007

On each run, an entry shall be reused when the lockfile's `inputHash` equals the current input hash and the entry's `questionHash` equals the current question hash. Only decisions without a reusable entry shall be sent to an oracle.

**Acceptance Criteria:**
1. Given a lockfile produced from `spec.md`, when `augur plan --spec spec.md` runs again with a stub server, then no HTTP request is made, the plan is byte-identical to the first run's plan, and the exit code is 0.
2. Given a lockfile produced from `spec.md`, when one character of `spec.md` changes and `augur plan` runs again, then all non-overridden decisions are requested from the API.
3. Given a lockfile whose `persistence` entry has a stale `questionHash`, when `augur plan` runs, then only `persistence` is requested from the API and the other entries are reused.
4. Given a replayed run, when the lockfile is rewritten, then reused entries keep their original `resolvedAt` values.

---

## L2-024: Forced refresh
**Traces to:** L1-007

`--refresh` shall ignore every lockfile entry. `--refresh <id>` (repeatable) shall ignore only the named entries.

**Acceptance Criteria:**
1. Given a complete matching lockfile, when `augur plan --refresh` runs, then every non-overridden decision is requested from the API.
2. Given a complete matching lockfile, when `augur plan --refresh persistence` runs, then only `persistence` is requested.
3. Given `--refresh colour`, when the command is parsed, then stderr says `colour` is not a catalog decision and the exit code is 2.

---

## L2-025: Lockfile integrity
**Traces to:** L1-007

The lockfile shall be written atomically (write to a temporary file in the same directory, then rename), with entries sorted by `id`, two-space indentation, LF line endings, and a trailing newline. A lockfile that cannot be parsed or has an unsupported `lockfileVersion` shall stop the run and shall not be overwritten.

**Acceptance Criteria:**
1. Given two runs that resolve the same answers in different orders, when the lockfiles are compared, then they are byte-identical apart from `resolvedAt` values.
2. Given a lockfile containing invalid JSON, when `augur plan` runs, then stderr names the file and the parse error position, the file is unchanged, and the exit code is 2.
3. Given a lockfile with `lockfileVersion: 99`, when `augur plan` runs, then stderr reports the unsupported version and the exit code is 2.
4. Given the process is terminated during the lockfile write, when the lockfile is inspected, then it is either the complete previous version or the complete new version.

---

## L2-026: Plan output
**Traces to:** L1-008

`augur plan` shall write the plan to stdout, or to the path given by `--out <path>`. The plan is JSON containing `planVersion`, `catalogVersion`, `solutionName`, an `inputHash`, and a `decisions` object mapping every non-skipped decision id to `{ "value": ..., "source": ... }`. Serialization shall use sorted keys, two-space indentation, LF line endings, and a trailing newline.

**Acceptance Criteria:**
1. Given a resolved run with `--name Contoso.Orders`, when the plan is written, then it contains `planVersion: 1`, `catalogVersion: 2`, `solutionName: "Contoso.Orders"`, the input hash, and one `decisions` entry per non-skipped decision.
2. Given the same resolved decisions, when the plan is written twice, then both outputs are byte-identical.
3. Given `--out plan.json`, when `augur plan` succeeds, then stdout is empty and `plan.json` contains the plan.

---

## L2-027: Solution name
**Traces to:** L1-008

`--name <SolutionName>` shall be required for `plan` and `generate`. It shall match `^[A-Z][A-Za-z0-9]*(\.[A-Z][A-Za-z0-9]*)*$`, be at most 64 characters, and no dot-separated segment shall be a C# keyword (compared case-insensitively).

**Acceptance Criteria:**
1. Given `--name Contoso.Orders`, when the command is parsed, then the name is accepted.
2. Given `--name ../evil`, `--name contoso`, `--name Contoso..Orders`, or `--name Contoso.Class`, when the command is parsed, then stderr states the naming rule and the exit code is 2.
3. Given a 65-character name that otherwise matches the pattern, when the command is parsed, then the exit code is 2.

---

## L2-028: Plan validation
**Traces to:** L1-008

`augur emit --plan <path>` shall validate the plan against the plan schema and the current catalog before emitting anything. Validation shall reject: unsupported `planVersion`; a `catalogVersion` different from the installed catalog; unknown decision ids; values outside a decision's answer set; `other` as a value; missing required decisions; a value present for a decision whose `when` clause is false; and an invalid `solutionName`.

**Acceptance Criteria:**
1. Given a plan hand-edited to change `persistence` from `ef-core-sqlite` to `ef-core-postgresql`, when `augur emit` runs, then the plan is accepted and the emitted solution uses PostgreSQL.
2. Given a plan with `architecture: "hexagonal"`, when `augur emit` runs, then stderr gives the JSON path `$.decisions.architecture.value` and the allowed values, no files are written, and the exit code is 2.
3. Given a plan with `architecture: "minimal-api"` and a `domain-complexity` value, when `augur emit` runs, then stderr says `domain-complexity` must be absent when `architecture` is `minimal-api` and the exit code is 2.
4. Given a plan whose `catalogVersion` is 0, when `augur emit` runs, then stderr reports the mismatch and the exit code is 2.
5. Given a plan file larger than 1 MiB, when `augur emit` runs, then stderr reports the size limit and the exit code is 2.

---

## L2-029: Plan schema
**Traces to:** L1-008

`augur schema plan` shall print a JSON Schema (draft 2020-12) describing `GenerationPlan` for the installed catalog, including the allowed values of each decision.

**Acceptance Criteria:**
1. Given catalog version 2, when the user runs `augur schema plan`, then stdout is a valid JSON Schema document and the exit code is 0.

1. Given each `ui-library` value and viewport widths of 375 px and 1200 px, when axe-core scans each emitted page with the `wcag2a`, `wcag2aa`, `wcag21aa`, and `wcag22aa` tags, then it reports zero violations.
2. Given any emitted page, when the user presses Tab once after the page loads, then a visible "Skip to main content" link receives focus; when it is activated, then focus moves to the `main` element.
3. Given any emitted page, when the user moves through it with Tab and Shift+Tab, then every interactive element can be reached and operated with the keyboard, and each one shows a visible focus indicator.
4. Given any emitted page, when its structure is inspected, then it has exactly one `main` landmark, one `banner` landmark, and one `navigation` landmark in the shell.
5. Given the user navigates between routes, when each route finishes loading, then `document.title` changes to a value unique to that route and focus moves to the route's top-level heading.
6. Given `ui-library=none` and the operating system set to reduce motion, when the navigation opens and closes, then no transition or animation longer than 0 ms runs.

## L2-057: Performance of generated Angular applications
**Traces to:** L1-013

Emitted Angular workspaces shall configure production budgets in `angular.json` of 500 kB (warning) and 1 MB (error) for the initial bundle, and 4 kB (warning) and 8 kB (error) for any component stylesheet. Every route other than the home route shall be lazy-loaded. The production build of the home page shall meet the Core Web Vitals "good" thresholds.

**Acceptance Criteria:**
1. Given any plan that emits an Angular workspace, when `angular.json` is inspected, then the production configuration contains the four budget values above.
2. Given any plan that emits an Angular workspace, when `ng build` runs, then no budget warning is reported.
3. Given any plan that emits an Angular workspace, when the production build output is inspected, then the not-found route's component is in a chunk separate from the initial bundle.
4. Given the production build served locally with `server-side-rendering=false`, when Lighthouse runs with its default mobile emulation against the home page, then Largest Contentful Paint is at most 2.5 seconds and Cumulative Layout Shift is at most 0.1.

## L2-058: Emission runs no external tools and makes no network requests
**Traces to:** L1-012

`augur emit` and the emission step of `augur generate` shall not start any external process (including `dotnet`, `npm`, `npx`, `node`, or `ng`) and shall make no network requests. All emitted content, including `package-lock.json`, shall come from templates bundled with Augur. Augur itself shall not require Node.js.

**Acceptance Criteria:**
1. Given a machine with no network access and a `PATH` containing no `npm`, `node`, `npx`, or `ng` executable, when `augur emit` runs for a `fullstack` plan using the installed tool, then it succeeds with exit code 0 and the output is byte-identical to the output of the same plan on a machine with network access.
2. Given any valid plan, when `augur emit` runs under process and network monitoring, then no child process is started and no network connection is opened.
